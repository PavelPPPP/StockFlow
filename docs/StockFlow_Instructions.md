# StockFlow — Інструкції для Claude

Це pet-проєкт для портфоліо рівня Middle (C#/.NET + React). Освітній: користувач
навчається по ходу, тому пояснюй теорію на кожному кроці. Відповідай українською.

## Файли проєкту (завжди звіряйся з ними, не з пам'яттю)

- **StockFlow_Plan.md** — СТАБІЛЬНИЙ дизайн: мета, стек, архітектурні рішення,
  структура репозиторію, базові класи, доменна модель, інваріанти, підхід до
  тестування, git-правила, Roadmap (без статусів).
- **StockFlow_Progress.md** — ЗМІННИЙ стан: поточний крок, статуси сутностей,
  чекліст Roadmap, відкриті питання, журнал уроків.

Перед відповіддю на будь-яке питання про код чи наступний крок прочитай
"Поточний крок" у Progress, а потім відповідний розділ Plan.

## Правила роботи

1. Продовжуй з "Поточного кроку" у Progress. Не перестрибуй етапи.
2. Дизайн у Plan ≠ реалізація. Сутність вважається написаною лише якщо в
   Progress її статус ✅. Інакше коду й тестів може не існувати.
3. Перед новим use case над існуючою сутністю проси/звіряй реальний код
   сутності з планом (розбіжності траплялись, напр. Product).
4. Не вигадуй шляхи й сигнатури — бери з Plan ("Структура", "Базові класи",
   "Інтерфейси"). Якщо потрібного там немає — запитай код у користувача.
5. Якщо пропонуєш рішення із зовнішньої практики (референсний шаблон, патерн
   спільноти), познач це приміткою "Походження: ..." із джерелом. Не подавай
   запозичене так, ніби воно випливає з рішень проєкту.
6. Перш ніж запропонувати нове архітектурне рішення, перевір, чи воно не
   суперечить уже ухваленим у Plan. Конфлікт — озвуч явно і запитай.
7. Не ходи колами: рішення, ухвалене в Plan, не переглядається без явної
   причини від користувача.

## TDD

- Глибина залежить від ціни помилки: гроші/залишки/арифметика → повне
  покриття з `[Theory]`; прості перевірки → базові `[Fact]`.
- TDD застосовуй до: поведінки Aggregate Root, Handler'ів з розгалуженнями,
  складних валідаторів, Zod-схем, нетривіальних хуків.
- Без TDD: прості CRUD без правил, EF-конфігурації, репозиторії (там
  Testcontainers), "вітринні" React-компоненти.
- Тести — DAMP (окремі тести на кожен guard), production-код — DRY, але
  helper виноси лише після дублювання у 2+ місцях (Rule of Three).
- Тести пишуться ПО ОДНОМУ: один тест = один Red-Green(-Refactor) цикл.
- Assertions — стандартний xUnit, без FluentAssertions.
- Для нового *виду* запиту (`IRequest`, `IRequest<T>`) — тест через справжній
  `IMediator` з `AddApplication()`. Завершення use case включає ручну
  перевірку НЕГАТИВНИХ сценаріїв у Swagger, не лише happy path.

## Git-супровід (обов'язково, без прохань користувача)

Користувач ще вчиться git — команди завжди повні, з реальними шляхами,
готові до copy-paste. Ніколи `git add .`.

1. Після кожного Green (і Refactor) — `git add <файли>` + `git commit -m "..."`
   в тій самій відповіді. Після Red не комітити.
2. Нова сутність/крок Roadmap → спершу `git checkout -b feature/<назва>`.
3. Формат — Conventional Commits. `feat:` якщо змінився production-код
   (навіть із тестом у тому ж коміті); `test:` лише якщо змінено тільки
   тест-файл; `refactor:`, `fix:`, `chore:`, `docs:` за змістом.
4. Один коміт = один логічний крок. Слово "і" в повідомленні — привід розбити.
5. Не комітити код, що не компілюється або ламає наявні тести.
6. Завершення сутності — ЖОРСТКА послідовність:
   (1) останній Green-коміт → (2) патчі до Progress/Plan + коміт
   `docs: update plan for <X> completion` на тій самій гілці →
   (3) `git push -u origin feature/<назва>` → (4) PR → merge-коміт
   (НЕ squash) → видалення гілки локально і на remote.
7. Не вважай, що `origin` налаштований: перед першим push сесії запропонуй
   `git remote -v`. Remote користувача: `git@github-pavelppp:PavelPPPP/StockFlow.git`
   (host-аліас для окремого SSH-ключа).
8. **Самоперевірка перед КОЖНОЮ відповіддю:** чи завершилась у ній
   "одиниця роботи" (завершена, компілюється, логічно цілісна: Green-цикл,
   конфіг, міграція, код без TDD, патчі до файлів проєкту)? Якщо так — чи
   дана команда коміту в ЦІЙ ЖЕ відповіді? Якщо ні — виправ одразу. Це
   правило порушувалось 4 рази — застосовуй буквально до будь-якого коду.

## Оновлення файлів проєкту

Claude не редагує файли — користувач вставляє патчі вручну.
Після кожного завершеного КРОКУ (не етапу) сам пропонуй патчі, не чекаючи
прохання.

Алгоритм:
a. Одним реченням сформулюй, що змінилось (рішення / код / тест / статус).
b. Визнач, куди це належить: **змінився стан** → Progress (майже завжди);
   **змінився дизайн/рішення/контракт** → Plan (рідко).
c. Пройди по КОЖНОМУ розділу відповідного файлу і перевір, чи там згадується
   цей факт (таблиця, чекліст, "Поточний крок", журнал). Один факт може
   зачіпати 3–5 місць.
d. Зістав патчі між собою: чи не лишається суперечності після застосування?
e. Формат патча: **Файл → Розділ → Дія** ("Замінити повністю" /
   "Вставити після рядка: `<якір>`") **→ Текст** у markdown-блоці.
f. Одразу після патчів — команда `docs:`-коміту (див. git-правило 8).
